## 一、AI 临时脚本静默清理

### 核心规则

为排查、校验、验证而**由 AI 自己创建的临时脚本/文件**，用完后**直接删除即可**，不需要向用户说明、不需要在回复里汇报删除动作、不需要询问是否保留。

### 适用范围

- 语法/编码校验脚本
- 环境排查脚本（如查询进程、端口、连接状态的一次性脚本）
- 数据转换、批量改写的中间脚本
- 任何 AI 为完成当前任务自行创建的 `tmp_*` / `temp_*` / 一次性脚本

### 约束

- **只删自己创建的**：仅删除本次会话中由 AI 生成的文件；用户已有文件、项目既有文件一律不动
- **命名可识别**：临时文件统一以 `tmp_` 或 `temp_` 前缀命名，便于识别与清理
- **优先复用工具能力**：能用内联命令完成的小校验，不额外落盘脚本；确需落盘时再创建，用完即删
- **不留在仓库**：临时脚本不得提交进版本控制，任务结束时工作区不应残留本次创建的临时文件

## 二、长时命令必须实时回显，禁止缓冲管道吞输出

### 1. 核心要求

执行**可能超过几秒**的命令（构建、重启服务、数据库操作、批处理脚本）时：
- 输出必须**实时可见**，让用户随时看到进行到哪一步；
- **严禁**把整段输出 pipe 给 `tail` / `grep` / `head` / `sed` 等缓冲/汇总类过滤器后再展示——这些过滤器会缓冲全部输出直到命令结束，期间用户看到的是**零输出**，必然误判为卡死。

### 2. 正确做法

- **启动/部署脚本**：裸跑（脚本自带分步日志，如每步有 `[n/N]` 进度）。
- **需要过滤输出**：拆成两步——先裸跑落盘（重定向到临时文件并 echo DONE），再单独查看/过滤该文件。
- **多阶段长任务**：拆成多条命令逐段执行，每条前 echo 进度（如 `[1/3] building...`），结束打 OK/FAIL。
- **会改变状态的命令**（重启服务 / 写 DB / 删文件）：执行前主动说明预计耗时，让用户能区分「正常慢」与「卡死」。

### 3. 禁止项

- 长命令的输出接 `tail -N`：输出全部缓冲到结束，执行期间零回显。
- 长命令的输出接 `grep xxx`：同上；且匹配不到时退出码还会误报失败。
- 一次性串起「构建 + 重启 + 验证」的长链条：中途无输出且无法中途确认；拆开逐步跑。
- 明知耗时却不预告耗时。

### 4. 例外：输出可能包含凭据时必须脱敏

裸跑上屏与凭据保护直接冲突——命令行是密钥泄露的头号渠道（连接串里的 `Password=`、k8s token、`Authorization` 头、`-p <密码>` 形式的参数）。

判断命令**可能**输出凭据时，按下述顺序处理：

1. **优先绕开**：改用不打印凭据的等价命令
   - 例：让用户以环境变量方式提供凭据，而非拼在命令行里；优先选用支持 `--mask` / 不回显凭据的参数
2. **先落盘再查看**：重定向到临时文件 → 对文件脱敏（替换敏感片段）→ 查看脱敏后的内容
3. **必须上屏时**：明确提示用户「以下输出可能含凭据，请注意」

> **关键区分**：真正被禁止的是「为了过滤就把输出 pipe 掉，导致执行期间零回显」，不是「任何过滤都不允许」。改用「落盘 + 事后过滤」两步走的写法，既满足实时进度可见，又完成了脱敏。

## 三、写操作必须幂等

### 核心规则

**任何会改变状态的命令，都必须能安全地重复执行。** 上下文压缩、会话重放、网络超时重试都可能导致同一条命令被执行多次。

### 做法

- 优先用幂等原语：`upsert` 优于 `insert`、带 `IF NOT EXISTS` 的建行优于裸建、写文件优于追加文件
- 无法幂等的命令（如先查后写），执行前**先做存在性检查**并报告检查结果
- 计数 / 累加 / 扣减类操作必须有**唯一约束或幂等键**兜底，不能只靠「先查了一下」

### 禁止项

| 禁止 | 说明 |
| --- | --- |
| 裸 `insert` 承载唯一语义 | 重试即产生脏数据，应靠唯一索引而非应用层判断 |
| 循环里执行非幂等写操作 | 失败重试会放大成多次副作用 |
| 用 `rm -rf` 表达「确保不存在」 | 应先用幂等的存在性检查，且该命令本身属 L3 不可逆操作（见《决策篇》§四.1） |

## 四、失败处理与重试纪律

### 核心规则

**命令失败后，不要原样重试**——重复执行一条注定失败的命令，只会消耗时间和上下文。

### 做法

1. 失败后先**读懂错误信息**，定位到具体原因（缺依赖？路径错？权限不足？参数版本不匹配？）
2. 修正 causes 后再跑；改正后重跑同一命令是合理的，**带着同一个错误重跑不是**
3. **同类失败连续 2 次**即停止重试：换策略、缩小范围，或带着错误输出向用户报告
4. 测试 / 构建失败时，**定位根因再改**，不能靠重跑掩盖偶发问题

### 禁止项

- 同一条失败命令**连续重试 3 次以上**而不改变任何参数或策略
- 把失败的输出当作成功继续往下走（尤其是 `grep` 不匹配导致的非零退出）
- 失败后改用更激进的手段绕过 —— 例如 `rm -rf` 解决权限问题、`--force` 解决推送冲突

## 五、环境隔离红线

### 核心规则

**命令行默认作用域必须是本地 / 测试环境，指向生产或线上的操作必须显式声明目标环境并取得确认。**

### 做法

- 一次性脚本、排查脚本、校验脚本、调试工具：**禁止连接生产数据源**
- 涉及多环境的操作（部署、迁移、配置下发），执行前明确写出「目标环境 = X」
- 不确定当前配置指向哪个环境时，先查证再动手，不假设
- `--host` / `--env` / `--db` / `--profile` 这类决定环境归属的参数，逐个确认其值为预期值

### 禁止项

| 禁止 | 说明 |
| --- | --- |
| 拿线上数据做只读实验 | 「只读」不等于无害，慢查询与大结果集同样影响生产 |
| 用生产凭据跑本地调试脚本 | 凭据扩散风险 + 误操作风险 |
| 未声明环境即执行变更 | 用户无从判断影响范围 |
