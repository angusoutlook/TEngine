# 合并结果必须查结果树，禁止由工作区存在性推演

> 沉淀来源：同一次会话中连续两次因本错误模式得出错误结论（TEngine 迁移方案评估中，误判 `.codex/mcp-tools.md` 合并后会回归、误判 `Assets/Launcher/` 需手工删除）。

## 一、触发场景

评估或执行合并 / 整合 / cherry-pick 类任务，凡需判断「合并后某文件、目录、配置项**是否存在**」或「内容取谁的」时，本规则生效。

## 二、错误模式（禁止）

把「分支 A 的工作区有 X、分支 B 的工作区无 X」直接推成「合并后 X 存在 / 不存在 / 有两份」。

典型违规话式：「A 有 B 无 → 合并后 A 版保留」「两边都有 → 合并后会重复」「A 新增了 X」。

## 三、为什么错

合并结果由 **base + 双方改动** 三方共同决定，**既不是双方工作区的并集，也不是交集**。只看 A/B 两方工作区，无法区分以下情形：

| base（＝ merge-base 共同祖先） | A 方 | B 方 | 合并后 |
|---|---|---|---|
| 有 X | 删除 | 未改（沿用） | **X 不存在**（删除生效） |
| 有 X | 未改（沿用） | 删除 | **X 不存在**（删除生效） |
| 无 X | 新增 | 无 | **X 存在** |
| 有 X | 修改 | 沿用 | **取 A 的版本**（B 的旧版被覆盖，无冲突） |
| 有 X | 修改 | 修改（不同处） | 自动合并或冲突，须实测 |

关键盲点：**「A 方工作区存在 X」既可能是 A 新增，也可能是 A 沿用 base**；**「B 方工作区不存在 X」既可能是 B 删除，也可能是 B 从未有过**。两者导致的合并结果完全相反。

> 注：`git diff A B` 的 `+/-` 符号同样有歧义——「A 相对 B 新增」往往正是「base 有、A 删、B 沿用」的反向表现，不可据此判定谁新增。

### 最容易失败的地方：选择性执行

本规则失效的主因**不是不知道方法，而是只对存疑项执行、其余偷懒**：对"看起来可能出问题"的路径查了结果树，对"显然会保留"的路径直接用 `git diff --stat` 的 `+/-` 写结论。

实际代价：一份 14 项的合并清单里，查过的 3 项全对，没查的 11 项中 **7 项写反**（把"base 有 / 一方删 / 另一方沿用"误判成"新增 → 保留"，反之亦然），且错误成对出现、互相掩盖，事后极难发现。

**要求：本规则对所有结论项逐项执行，不设"看起来没问题"的豁免。** 越是"显然保留"的项越要查——错误恰好集中在那里。

## 四、正确做法（逐步）

1. **定方向**：`git merge-tree --write-tree <目标分支> <来源分支>`，读作「站在目标分支上，合入来源分支」。
   - ⚠️ **「目标分支」不是 merge-base**：本文件 §三 表格中的 `base` 专指 **merge-base（共同祖先）**，与上句的「目标分支」是两个概念，勿混。
   - 站 B 上执行 `git merge A` → 对应 `git merge-tree --write-tree B A`
   - 写反会让 modify/delete 的判定方向相反。
   - 需 **git 2.38+**（旧版无 `--write-tree`）。
2. **取结果树 OID**：命令首行输出即结果树 OID（冲突时退出码非 0 但 OID 仍可用）。
3. **查存在性**：`git ls-tree --name-only <结果树OID> <路径>`。输出为空即该路径不存在。
4. **查内容取谁的**：`git rev-parse <结果树OID>:<路径>` 与 `git rev-parse <分支>:<路径>` 比对 blob OID——**相等即逐位相同**，可据此断言「合并后取的是某分支版本」。
5. **三方存疑补查 base**：`git ls-tree --name-only <merge-base> <路径>`，区分「新增」与「沿用」。
6. **结论写明取证方式**：结论须注明「由结果树 OID 直接查验」，不得写成「由双方工作区推断」。

## 五、注意

- 结果树 OID 是**临时对象，可能被 gc**；取证后及时把 OID 记录在产出中，便于复核。
- 结果树只反映 **git 层**合并结果，不反映语义正确性（如文档是否过时、代码是否还编译得过）——那是另一回事，须另行核验。
- 本规则约束的是**取证方式**，不改变动代码的授权边界（是否可写仍由《决策篇》§一 决定）。

## 六、自查

- [ ] 判断「合并后存在/不存在」时，是否查了结果树而非工作区？
- [ ] `merge-tree` 参数顺序是否与实际合并方向一致？
- [ ] 判断「取谁的版本」时，是否比对了 blob OID？
- [ ] 是否补查了 base，区分「新增」与「沿用」？
- [ ] **是否对清单里的每一项都查了？有没有对"看起来显然"的项用 `diff --stat` 符号带过？**（最高频失分项）
- [ ] 结论是否写明了结果树 OID，可供他人复核？
